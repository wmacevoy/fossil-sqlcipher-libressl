# embed/ — in-process Fossil proof-of-concept

**Status: proof-of-concept, not a supported build target yet.** Originally developed in the `fossil-app` project (2026-08-13) to answer one question for that project's iOS Flutter client: can Fossil's client operations run *in-process* — one process, no fork/exec, `exit()` trapped — invoked repeatedly, the way a `dart:ffi` shim must call them? Promoted here so any consumer of fossil-see (not just fossil-app) can build an FFI-style embedding on a shared, verified foundation instead of re-deriving it.

`harness.c` simulates the constraint on Linux by linking Fossil's objects into a harness (`main` renamed, `exit()` wrapped into a `longjmp`, `fossil_main()` called like a function).

## Proven (Linux + macOS, portable — see "Portable exit trap" below)

1. **Repeated in-process invocation works.** version -> init -> open -> settings -> add -> commit -> commit -> timeline -> status, all in one process, all rc=0. `fossil_main` does `memset(&g,0,...)` on entry — the main global is designed to re-init per call.
2. **The process survives `fossil_fatal`.** An intentional failure (empty commit) longjmps back; subsequent commands still work.
3. **The full networked lifecycle works in-process over HTTP:** clone -> open -> add -> commit (with autosync pull, server check-in lock, push) -> push/pull/sync — **when it is the only repository touched in the process.** The sync client never forks — fork exists only in the *server* loop, ssh/`file://` transports, external-tool launches, and backoffice. See "Cross-repo switching in-process — now with a repro" below for the one combination that does *not* work yet.
4. **The exit-trap now works on Apple's linker, not just GNU ld** (2026-08-13). `harness.c` was rebuilt and rerun on macOS/arm64 with zero linker tricks: local-only phase all-pass, and the networked phase separately all-pass (clone/open/add/commit-with-autosync/push), both via `fossil_embed_init()` (see below), neither via `-Wl,--wrap=exit`.

## Bug found and fixed (why this experiment mattered)

**Delete-on-failure carryover — catastrophic class.** `init`/`open` register "delete this file if we fail" entries (the repo! `.fslckout`!) in a file-static list that is *never* cleared between in-process calls. A later `fossil_fatal` fired the stale list and **deleted the repository**. Fix: `../build/patches/fossil-db-embed.patch`, a 12-line patch adding `db_clear_delete_on_failure()`, called by the shim after every command. Found in an hour with this harness, instead of in the field on a phone.

## Required shim rules (all verified)

- Call `db_clear_delete_on_failure()` after every command.
- Call `sqlite3_shutdown()` between commands (fshell precedent).
- Set `backoffice-disable=1` on every repo at open/clone — and compile backoffice's `fork()` out entirely for constrained platforms (`#ifdef`), belt-and-braces.
- No interactive prompts ever: clone with `--save-http-password`, pass `--user`, pre-answer everything via flags.
- Serialize commands (one at a time) — Fossil is not re-entrant concurrently.
- One repository per process lifetime for a v1 embedding. A handful of function-statics cache repo identity forever (e.g. `db_repository_filename`'s `zRepo`, the versioned-settings cache, static prepared statements). Cross-repo switching in-process misbehaves (observed: commit consulted the wrong checkout). A real multi-repo embedding needs a `fossil_embed_reset()` that clears an auditable, grep-able list of statics — not attempted here.
- Handle check-in lock contention in the embedding's UX: autosync commit takes a server-side parent lock; on "Might fork / parent locked", auto-`update` and retry (or `--override-lock` after the ~60s timeout).

## Portable exit trap — done (2026-08-13), and why it's shaped the way it is

**Read this before touching `fossil_exit()`, `fossil_panic()`, or `fossil_fatal()` again — the reasoning below was arrived at the hard way (three independent reviews plus empirical testing) and is meant to save whoever's next from re-deriving it.**

`build/patches/fossil-embed-exit-trap.patch` adds `fossil_embed_init(void (*handler)(int))` (`util.c`, next to `fossil_exit()`). Register a handler once, before any `fossil_main()` calls; `fossil_exit()` calls it instead of libc `exit()` when one is set (default: unset, byte-identical stock CLI behavior — this is why it was safe to apply unconditionally, unlike a hypothetical patch that changed default behavior). The handler must never return (see the patch's own comment for why, and what happens if it does).

**Design choices, and why the obvious alternatives were rejected:**

- **A bare static function pointer in `util.c`, not `struct Global` (`g`), and not an opaque "session" object.** `g` is `memset()`-zeroed at the top of every `fossil_main()` call, which would wipe a handler stored there on every single command. A session/handle-based API was considered and rejected *for now*: Fossil's internals (`g`, the static `Stmt` cache, `db_repository_filename()`'s static `zRepo`, the versioned-settings cache) are a process-wide singleton by about twenty years of deliberate design, not an oversight a handle would paper over — building a fake multi-instance API today would promise concurrency semantics nothing underneath actually provides. Named `fossil_embed_init()`, not something `fossil_exit`-specific, so a future `fossil_embed_reset()` (per-repo-switch lifetime, see below — still not built) has an obvious sibling to sit next to without a public-symbol rename later.
- **Two other bypasses were fixed in the same patch, not left as follow-ups**, because leaving them silently defeats the whole mechanism: `fossil_fatal()`'s reentrancy-guard (`static int once`) used to call a raw `exit(1)` on the *second* fatal error in the process's lifetime — since `once` is a plain C static, never touched by `fossil_main()`'s per-call `memset`, this meant the first fatal error of a process would be trapped correctly and every one after it would silently kill the host app anyway, looking exactly like the trap "stopped working" with no code change in between. Also fixed: a raw `exit(1)` in `content.c`'s `test-integrity --db-only`/`--quick` path — a real, client-reachable command, not gated by server/CGI context.
- **`fossil_panic()`'s `abort()` is deliberately NOT touched**, on both its own `once`-guard bypass and its normal path. Two reasons, not one: (1) Fossil's own doc comment above the function says panic-class errors are meant to end in `SIGABRT` unconditionally — that's "should-never-happen bug" territory, distinct from `fossil_fatal()`'s "bad user input" territory, and silently redirecting it into "keep the host app alive" would contradict what the function is documented to guarantee; (2) the `once` guard exists specifically so a *second* panic during first-panic handling does less work, not more — routing it through more machinery (`fossil_exit` -> `db_close` -> ... -> possibly panicking again) would work against the one thing the guard exists to prevent. **Net effect, stated plainly: an in-process embedding can still have its whole host process killed by any of `fossil_panic()`'s 79 call sites** (several plausibly reachable from ordinary operation — delta-loop/corruption checks in `content.c`, `db_protect()`/`db_unprotect()` call-balance checks in `db.c`), **with no recovery.** This is an accepted, named v1 gap, not an oversight — audit reachability from whatever command surface an embedding actually exposes before assuming it's covered by "the exit trap."
- **`assert()`, separately** — this build compiles Fossil's own ~512 `assert()` call sites live (no `-DNDEBUG` for Fossil's own objects; only the vendored SQLite gets it, via `main.mk`). Every one is also a live, untrappable `abort()`. Not addressed here; needs its own explicit decision (accept the risk and document it, or wrap `assert` through the same handler for Fossil's translation units) before a real embedding ships.

**Verification:** `harness.c` was rewritten to use `fossil_embed_init()` instead of `-Wl,--wrap=exit` and rerun; see "Proven" above. Compiling the harness against Apple's linker needed one more portability fix along the way, unrelated to the exit trap itself but blocking testing it: the original recipe used `objcopy --redefine-sym main=fossil_cli_main`, a GNU-binutils tool absent on macOS (confirmed: no `objcopy`, no `llvm-objcopy` via `xcrun`). Fixed by recompiling `main_.c` with `-Dmain=fossil_cli_main` instead — a plain C compiler flag, portable to every platform this project targets, needing nothing `objcopy` gave that a `#define` doesn't. See `harness.c`'s own header comment for the exact recipe.

## Cross-repo switching in-process — now with a repro, not just a warning

The original bullet list below already named this risk ("Cross-repo switching in-process misbehaves (observed: commit consulted the wrong checkout)") but had no standing reproduction. There is one now: run `harness.c`'s combined local-only-then-networked phases back to back in one process (`./harness --net URL`) and the networked phase's `commit` fails with **no printed error at all** (silently returns rc=1 — traced to `fossil_print_error()`'s output path, not yet root-caused further). Run the exact same networked sequence (clone/open/add/commit/push) *alone*, in its own process with no prior repo touched — confirmed all-pass, on the same binary, same server, same machine. So this is conclusively a same-process cross-repo state-carryover bug, not a fluke of one run, not something the exit-trap patch introduced or fixes, and not present when the "one repository per process lifetime" rule (already stated below) is actually followed. Whoever builds `fossil_embed_reset()` should start from this repro rather than reconstructing one.

## iOS-specific constraints beyond the exit trap — read before writing Swift/Dart glue

Findings from a dedicated review pass (2026-08-13), not yet acted on in code:

- **The single biggest unverified risk is `setjmp`/`longjmp` across an ARC/Swift stack frame, and it fails *silently*, not loudly.** `longjmp` does a raw register restore; it knows nothing about Objective-C/Swift frame semantics. Any ARC-managed strong reference, `defer` block, or autorelease-pool push sitting on the stack between the `setjmp()` and the matching `longjmp()` gets skipped — not a crash, just silently-never-run cleanup, leaked objects, or (worse) an unbalanced autorelease pool that corrupts unrelated code much later. This needs a hard, enforced architectural rule: the FFI entry point must be a pure C function called directly by `dart:ffi`, with nothing else — no Swift, no ObjC — between it and both ends of the jump, for the entire life of the app. That invariant is easy to break by accident with completely idiomatic iOS patterns (wrapping the call in a `Task {}`, calling from a delegate callback) and the breakage would not show up as a test failure — verify with Instruments/Leaks on a real device, not just "it compiles and returns a value."
- **Fossil's client HTTP transport has no timeout at all** (`http_socket.c`/`http_transport.c` — no `SO_RCVTIMEO`, no connect timeout; `fossil_set_timeout()` is server-path-only). A stalled mobile network can hang a sync call indefinitely. The natural fix — a watchdog thread force-closing the socket — surfaces as an I/O error, which is one of the plausible real-world ways to hit the undocumented `fossil_panic()` gap above rather than a clean, trappable `fossil_fatal()`. "Cancel a hung call" and "the exit-trap catches everything" are currently in tension, not aligned; needs its own design.
- **Fossil's globals are confirmed non-thread-local and Fossil is confirmed non-reentrant** (`Global g` in `main.c` has no `__thread`/`_Thread_local` anywhere in the tree). `dart:ffi` guarantees a synchronous call blocks the calling isolate — it does **not** guarantee that isolate stays pinned to one OS thread across the app's lifetime, and Flutter's own standard pattern for not blocking the UI thread (`Isolate.run`/`compute()`/background isolates) actively works against that assumption. The embedding must build and enforce its own single dedicated serializing worker thread; nothing here or in Dart provides that for free.
- **Good news, worth keeping true rather than re-verifying from scratch:** the SIGSEGV/SIGPIPE/SIGTERM/SIGINT handler registrations in `main.c` are confirmed wired up *only* inside `cmd_webserver`/`process_one_web_page` (the HTTP-server code path) — never in general client-command dispatch. As long as a mobile shim's command allowlist permanently excludes `server`/`ui`/`http`/`cgi`/`fuse`, the async-signal-safety hazard of a signal handler triggering a longjmp is avoided by construction. Enforce that allowlist explicitly in the shim; don't rely on it being merely unused.
- **Cross-compilation to arm64-apple-ios is completely unattempted anywhere in this repo** — not Fossil's own `./configure`, not SQLCipher against *this project's specific* LibreSSL choice (precedent exists for SQLCipher-on-iOS via CommonCrypto; none found here for the LibreSSL path this project actually uses), not LibreSSL itself. Packaging shape (`XCFramework`) also undesigned. This is a real, separate body of work from the exit-trap fix, not a detail to discover mid-integration.
- **iOS filesystem-sandbox realities are untested**: `NSFileProtectionComplete` making the repo file inaccessible while the device is locked mid-write, iCloud-backup inclusion/exclusion for the repo file, and multi-process (app + extension, via App Group) access to the same repo — a known historical SQLite-in-App-Group corruption class, never checked against Fossil's own locking model specifically.

## What's still open before this is a real build target

- **Output capture.** Fossil prints to stdout; a real embedding needs per-call redirection to a buffer, or should use Fossil's built-in JSON command API (`fossil json timeline`, etc., already compiled in) as the structured interface instead of scraping text output — though note the JSON API is *not* a separate invocation mechanism, it's layered on the same `fossil_main(argc,argv)`/stdout path, just easier to parse. The one place worth skipping the argv/stdout shim entirely: SQL queries, which can go straight through `db.c`'s `db_prepare`/`db_step`/`db_column_*` functions with zero argv parsing involved.
- **`fossil_embed_reset()`** (per-repo-switch lifetime) — see "Cross-repo switching in-process" above for why this now has a concrete repro to build against, not just a warning.
- **Cross-compilation** to each target ABI (arm64-apple-ios, Android NDK, etc.) — see "iOS-specific constraints" above.
- **Packaging as `libfossilsee`** (static or shared library + a small, stable C API) hasn't been designed; `harness.c` is a one-off test program with its own `main()`, not a library. Recommended shape from the API-design review: narrow surface (open/wiki-read-write/ticket-read-write/sql/sync only, matching what the sibling `viki` project actually needs), with the `fossil_embed_init()` exit-handler wiring kept entirely internal — callers should never see `fossil_exit`/`fossil_embed_init` in their own headers. **Tickets specifically must stay on the argv shim (`fossil ticket set`/`show`), never raw SQL writes** — `tkt.c` has no create/update function-level API, and the `ticket`/`tktchng` SQL tables are a materialized view of DVCS-versioned artifact history; writing them directly would desync the hash-chained history from the queryable data, a real silent-corruption risk, not just an unsupported path.

## Build (historical recipe, Linux + GNU ld only, from a `build/build.sh` output tree)

```
objcopy --redefine-sym main=fossil_cli_main <fossil-build-dir>/bld/main.o <fossil-build-dir>/bld/main_h.o
cc -o harness harness.c <fossil-build-dir>/bld/*.o \
   -Wl,--wrap=exit -lresolv -lssl -lcrypto -lz -ldl -lpthread -lm
./harness            # local-only phase
./harness --net URL  # also exercises the networked lifecycle against URL
```

Not run as part of `build/build.sh` — this directory is not yet wired into the standard build.
